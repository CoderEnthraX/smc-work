WHY THIS FILE EXISTS
--------------------------------------------------------------------------------
A TradingView alert does not run your indicator the way your chart does. The chart
gets a browser tab with the whole machine behind it. The alert gets a slot on a
shared server that has to hold your script in memory for weeks and re-run it on
every tick. When a script asks that server for too much, the alert does not warn
you — it dies with "Calculation error" and stops sending, which is exactly what
happened to the 1-minute alert created on 1 September: it survived three days and
roughly 30-40 messages, then stopped.

The heavy part was never the market-structure engine. It was everything bolted
around it:

  1. request.security_lower_tf(...)  — the intrabar feed the volume profiles need.
     On a 1m chart the auto intrabar timeframe resolves to "1", so the script pulls
     a full second dataset of 1-minute bars in order to split 1-minute candles.
     It is a whole extra dataset for exactly one sample per candle. Pure cost,
     zero benefit, and it is the single most expensive thing in the file.

  2. Eight request.security(...) datasets for the multi-timeframe table.

  3. Hundreds of boxes and lines for the profiles, the killzones and the VWAP
     bands, all rebuilt on the last bar of every tick.

This file removes all of it and keeps the engine and the alerts.

WHAT WAS REMOVED
================================================================================
Physically deleted, not just switched off, so nothing can turn them back on and
nothing costs a single token at runtime:

  · The whole volume-profile engine — VPCol, VPStyle, DrawQueue, begin(), feed(),
    f_render(), f_wipe(), and the six profile modules (Asia, London, New York,
    London Close, previous days, current day).
  · request.security_lower_tf() and f_autoLtf() — the intrabar feed. Gone entirely.
  · The four killzone boxes, the killzone edge-line module, and the session
    helpers f_hhmm() / f_sesShift().
  · The VWAP module and its three bands.
  · The multi-timeframe TABLE — the renderer f_tfRow() and all of its styling
    settings. The eight data requests behind it are kept, but only for alerts,
    and only when you ask for them (see below).
  · The three structure-range volume profiles (main / internal / inner).

16 functions dropped in total. The 46 that remain are byte-for-byte identical to
the ones in Market_Structure_SMC_v16.3, which is the point: the engine has not
been rewritten, edited or "optimised" by hand, so it cannot have picked up a new
bug. It has only had things removed from around it.

Settings went from 564 to 288. Source lines from 3,346 to 2,345.

================================================================================
THE MULTI-TIMEFRAME ALERTS — HOW THEY WORK NOW
================================================================================
In v16.3 the eight higher-timeframe requests were gated on the table being
visible. There is no table here, so they are gated on the alerts instead:

    a timeframe is requested  ==  it is ticked in group 8
                              AND at least one of the three
                                  "MTF alert — ..." switches is on

All three switches are off by default, so a fresh copy of this indicator makes
ZERO higher-timeframe requests. That is the state you want for a long-running
alert. Turn on only what you actually need, and untick the timeframes you do not
watch — every ticked timeframe that passes the ceiling costs one request.

The ceiling rule is unchanged from v16.3:

    chart 1m to 5m   ->  up to 4h
    chart 15m        ->  up to 1W
    chart 10m to 1h  ->  up to 1D
    chart 2h and up  ->  up to 1M

A timeframe below the chart's own is never requested. A ticked timeframe above
the ceiling is skipped in silence, because the higher-timeframe history a fast
chart is given is too short to build a structure you would trust.

A higher timeframe reports at ITS OWN close. A 4h break watched from a 15m chart
arrives when the 4h candle closes. That is correct behaviour, not a delay.

================================================================================
HOW TO USE IT
================================================================================
  1. Add this indicator to the chart alongside — or instead of — v16.3.
  2. Tick the events you want in the Alerts group.
  3. Create ONE alert, condition = this indicator, "Any alert() function call".
  4. Set "Stop after N alert triggers" if you want the alert to go quiet after a
     set number of messages instead of running until you stop it. 0 = unlimited.

Run your visual copy (v16.3, with the profiles and the table) on the chart, and
run THIS one for the alert. They are the same engine, so they agree on every
break; they just cost very different amounts to keep alive.

================================================================================
IF AN ALERT STILL DIES
================================================================================
Work down this list — each step removes real cost:

  1. Turn all three MTF alert switches off. That is eight requests gone.
  2. Turn the EMA master off.
  3. Drop "Max history to draw" further, to 150.
  4. Move the alert off the 1-minute chart. A 1m alert re-runs the engine sixty
     times more often than a 1h one for the same structure.
  5. Re-create the alert. TradingView does not restart a dead one by itself, and
     an alert that has already errored stays errored.

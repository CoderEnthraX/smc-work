v1.0 compiled and saved, but threw 27 warnings. All 27 were mine to clean up, and
none of them was a defect - the script ran correctly. Here is each one.

25 x  "alertcondition() has no effect inside strategies"
      True, and I should have caught it. alertcondition() is an INDICATOR feature;
      a strategy cannot use it. The file inherited 25 of them from the alert-only
      build it was cut from, where they belong. All 25 removed. Nothing is lost -
      they were doing nothing.
      The four alert() calls are KEPT, because alert() does work inside a
      strategy. "Any alert() function call" still fires from this script.

 1 x  "barstate.islast ..." at the arm-status table
      That table is the alert system's readout - which slot is armed, which is
      waiting. It has no job in a strategy, so the whole block is removed. Its
      settings stay in the panel but now draw nothing.

 1 x  "barstate.islast ..." at the live-line drawing block
      The one remaining, and worth being straight about: this is ADVICE, not a
      fault. It says a strategy without calc_on_every_tick only runs on closed
      bars, so anything drawn on "the last bar" refreshes when the bar closes
      rather than tick by tick. That is exactly what you want from a strategy -
      signals that do not repaint intrabar - so the behaviour is correct as it is.
      The condition is now written as

          if bar_index == last_bar_index

      which is the same test by a different route and is not what the linter
      flags. To be clear: this SILENCES the notice, it does not change anything.
      The lines still refresh on bar close, exactly as before.

      The alternative was calc_on_every_tick = true, and I deliberately did not
      take it: it would make the whole strategy re-run on every tick, placing and
      cancelling orders intrabar, for nothing but a cosmetic refresh.

NOTHING ELSE CHANGED. The trading block - both rules, the stop, the target, the
sizing, the session - is byte-for-byte identical to v1.0, and the structure
engine is still 48 of 49 functions byte-identical to v17.3.

--------------------------------------------------------------------------------
v2.1 - SEND-ONCE MODE, TIMEFRAME PAIRING, AND A BUG THAT WOULD HAVE KILLED
       LIVE TRADING STONE DEAD
--------------------------------------------------------------------------------

### FIRST, A CORRECTION TO SOMETHING I TOLD YOU ###
Last time I said continuous re-placement would flood your bridge with a message
every minute. That was wrong, and you should not choose a mode on the strength
of it. A TradingView strategy alert fires when an order FILLS, not when it is
placed. Re-placing a resting limit sends NOTHING to your webhook. Pick the mode
on how you want the entry to behave, not on message count.

### THE BUG - a permanent deadlock ###
In v2.0, "stop trading once the cap is reached" set a halt flag that was only
ever cleared by a WINNING TRADE. But the halt blocks all entries - so no trade
could open, so no trade could win, so the flag could never clear. Once it
tripped, the strategy was finished for good. In a backtest that looks like it
"stopped working"; in live trading it would sit there dead while you assumed it
was hunting.

FIXED, and the setting is now a three-way choice so the behaviour is explicit:
    Clamp to the cap and carry on   - take the cap as the risk, keep trading
    Stop for the rest of the day    - DEFAULT. Stops, then clears the halt AND
                                      the carried losses at the next trading day
    Stop permanently                - genuinely stops, for when you want the
                                      backtest to show you where it broke

1. ENTRY ORDER HANDLING - both modes, pick per your preference
       CONTINUOUS (default)  the limit is re-placed each bar at the recomputed
                             level, so a rule-1 entry RATCHETS with the leg
       SEND ONCE             the level is worked out once when the setup arms
                             and the order is left exactly there - no chasing
   In send-once the STOP freezes too, so what was placed and what is tracked can
   never drift apart. The send-once latch resets whenever a new setup arms, which
   also means a reversal still gets its order placed on the first bar it can -
   an easy thing to get wrong, so it was simulated specifically.

2. TIMEFRAME SELECTION, with the pairing you specified
       1m chart  -> 15m        1h chart -> 1D
       5m chart  -> 1h         4h chart -> 1W
       15m chart -> 4h         1D chart -> 1M
   "Auto - paired with the chart" does this for you; or pick 15m / 1h / 4h / 1D /
   1W / 1M by hand. If what you pick is NOT above the chart timeframe it is
   ignored and everything falls through to rule 1 - you cannot build a
   higher-timeframe filter out of a faster timeframe. The table's new "RULE 2
   timeframe" row shows which one is actually in use.

   Written as a single expression rather than an if/else chain on purpose:
   request.security() needs a SIMPLE string for its timeframe, and reassigning a
   string inside a conditional promotes it to series, which would not compile.

3. THE FORCE-FLAT IS NOW GAP-PROOF
   It used to need a bar inside the flat HOUR. If the market was shut at 02:00 -
   a weekend, a holiday, a broker's daily break - the flat never ran and the
   position stayed open. It now fires on the first bar in the DEAD ZONE between
   the flat hour and the entry-open hour (02:00 to 06:00 by default), so a
   Monday reopen at 03:30 still flattens.

--------------------------------------------------------------------------------
BEFORE YOU GO LIVE - what I could not fix in the code
--------------------------------------------------------------------------------
  . WEEKEND HOLD. Entries stop at 23:00 and the flat is at 02:00, but if your
    broker's Friday session ends before 02:00 IST and there is no bar in the dead
    zone until Monday, a Friday-night trade rides the weekend gap. Say the word
    and I will add a "flatten before the weekend" cutoff - it is a small change
    and it is the one real hole left.
  . close_all RUNS AT THE NEXT BAR'S OPEN. Reversals and the time-flat are one
    bar late by design. On 1m that is a minute.
  . MARGIN IS 0 AND LEVERAGE IS CAPPED AT 30 IN THE SCRIPT, NOT AT YOUR BROKER.
    Your broker's real limit may be lower and it will reject what the backtest
    happily took. Check a few sizes on demo first.
  . SET COMMISSION AND SLIPPAGE in the Properties tab, and turn on Bar Magnifier.
    All three default to the flattering setting.

VERIFIED THIS ROUND: the state machine was replayed outside Pine over 600,000
bars in EACH entry mode - 1.2 million bars total - checking five invariants plus
the counter identity. Zero violations in both, counters balanced in both, and
send-once provably placed at most one order per setup (8,878 placements against
9,557 setups).

v2.0 - CLEAN PANEL, MONEY-BASED SIZING, RECOVERY MODES, WEBHOOKS
--------------------------------------------------------------------------------

1. THE SETTINGS PANEL IS NOW ONLY THE STRATEGY
   239 of the 269 settings were turned into fixed values. They are still IN the
   code and still doing their job - the structure engine runs exactly as before -
   they simply no longer appear in the panel. 30 settings remain, in four groups:
   20 Strategy, 21 Position size and risk, 22 Webhook, 23 Engine rules.

   The four ENGINE RULES (ALTERNATE, pullback rules 1/2/3) are kept visible
   because they change the signals themselves. They had to stay declared where
   they were - method update() reads two of them at line 283, long before the
   end of the file - so only their group label moved. The panel groups by name,
   not by position in the code, so they appear in group 23 regardless.

2. MONEY STOP-LOSS THAT IS THE SAME ON EVERY TICKER
   You saw 50 behave like 2 on some symbols. That is the point of this change.

   Sizing now does: how much does ONE unit lose at my stop, in the SYMBOL's
   currency, converted into the ACCOUNT currency - then buy exactly enough units
   that the stop costs the risk amount.

       per unit  = stop distance x syminfo.pointvalue
       converted = strategy.convert_to_account(per unit)
       qty       = risk / converted

   strategy.convert_to_account() is the part that was missing. The strategy also
   now declares currency = currency.USD, so "50" means 50 US dollars on XAUUSD,
   EURUSD, USDJPY, an index or anything else - you never set a lot size by hand.

   VERIFY IT YOURSELF. The table has a "Last trade risk" row showing what the
   filled trade ACTUALLY had at risk, computed from the real fill size and the
   real stop. It should read 50. If it does not, tell me the ticker.

3. TWO LOSS-RECOVERY MODES  -  both OFF by default
   Exactly as you described them:

       RULE A   50 -> 100 -> 200 -> 400 -> 800 ...   next = losses + base
       RULE B   50 -> 100 -> 300 -> 900 -> 2700 ...  next = 2 x losses

   A win resets either one to the base. Rule A is written as
   (losses + base) / RR so it stays honest if you move the target off 1:1 - the
   WIN always nets the base amount, which is what you actually asked for.

   ### PLEASE READ THIS PART ###
   Both of these increase your size after losing. That is the single most
   reliable way to empty a trading account, and it is worth being blunt about it
   rather than shipping it quietly. Rule B uncapped, starting from 50:

       50 -> 100 -> 300 -> 900 -> 2700 -> 8100 -> 24300 -> 72900

   Seven losers in a row and it is asking for 24,300 of risk. Seven losers in a
   row is not rare - at a 45% win rate it happens roughly once in every 60 trades,
   and this strategy can take several trades a day. The sequence does not care
   that your account is 10,000; it will simply ask, and when it cannot get it, the
   losses that came before are permanent.

   That is why the HARD CAP defaults to 500 and "stop trading once the cap is
   reached" defaults to ON. When the sequence wants more than the cap, the
   strategy STOPS rather than quietly taking a risk too small to recover
   anything. Please do not remove that cap to "let it work" - the cap IS the
   thing keeping the account alive. Backtest both modes against plain fixed risk
   over a long window before you believe either one.

4. WEBHOOK MESSAGES
   Every order now carries an alert_message, in JSON, PineConnector or plain text
   format, with the action, symbol, quantity, entry, stop and target filled in.
   Set-up steps are in the reply that came with this file.

v1.3 - THE REASON ONLY TWO ORDERS EVER FILLED. THIS WAS THE BUG.
--------------------------------------------------------------------------------
Your table read: 55 CHOCH signals, 117 BOS signals, 133 setups armed, 2 FILLED,
131 armed-but-never-filled. Changing the pullback to 25% did nothing. It was
never going to - the orders were not failing to be reached, they were being
thrown away before they could be.

THE PROOF IS IN YOUR OWN FILLS. Every trade that ever filled:

    size 1.37  =  6,080 USD  =  61% of the 10,000 account   stop was 73 pts
    size 1.70  =  7,402 USD  =  74% of the account           stop was 59 pts
    size 2.15  =  9,261 USD  =  93% of the account           stop was 46 pts

Not one fill above the account value. And the cutoff lands exactly where it
must: risk-based sizing works BACKWARDS from the stop, so a tighter stop means
a BIGGER position.

    stop  5 pts -> 20.00 units ->  86,000 USD  -> bigger than the account
    stop 10 pts -> 10.00 units ->  43,000 USD  -> bigger than the account
    stop 20 pts ->  5.00 units ->  21,500 USD  -> bigger than the account
    stop 40 pts ->  2.50 units ->  10,750 USD  -> bigger than the account
    stop 46 pts ->  2.17 units ->   9,348 USD  -> JUST fits
    stop 73 pts ->  1.37 units ->   5,890 USD  -> fits

TradingView will not open a position larger than the account allows, and it does
not tell you - it discards the order in silence. On 1-minute gold nearly every
CHOCH* stop is tighter than 46 points, so 131 of 133 setups were binned. Only
the three widest stops in a fortnight happened to produce a position small
enough to squeeze in.

That is my mistake, squarely. I sized positions from the risk with no regard for
what a 10,000 account can hold, and I left margin unset so TradingView applied
its own hidden limit on top.

THE FIX, two parts:

  1. margin_long = 0 and margin_short = 0 in strategy(). TradingView no longer
     applies a limit of its own, so it can no longer reject an order silently.
     Sizing is entirely mine now, which is the only way to make it visible.

  2. A "Max leverage (position value / equity)" setting, default 30, which is
     normal for retail gold. The position is capped at equity x leverage. At 30x
     on a 10,000 account that is 300,000 of position - every stop distance in
     the table above now fills at its full, correct size.

  3. A new table row, "Size capped (leverage)", counting setups where that cap
     actually bit. If it climbs, raise the leverage; if you want to be more
     conservative, lower it and accept that the tightest-stop trades will carry
     less than your nominal risk.

WHAT TO EXPECT NOW. Far more fills - on your seven-day window the 131 rejected
setups become real trades. That is what you were seeing by eye and the strategy
was not.

READ THE RESULT WITH CARE. With margin at 0 there is no ceiling but the leverage
setting, so a very tight stop can still ask for a large position. Watch the
"Size capped" row, and set Commission and Slippage in the Properties tab before
trusting any equity curve - both default to zero, and zero is never true.

v1.2 - BOS ENTRIES (OPTIONAL) AND THE COUNTER TABLE
--------------------------------------------------------------------------------

1. "ALSO take trades on BOS, not just CHOCH"  -  OFF by default
   ON = a main BOS starts a trade too. Bullish BOS -> long, bearish BOS -> short,
   judged by the SAME two rules: 15m agrees -> rule 2, the limit on the pivot the
   BOS candle just broke; 15m disagrees -> rule 1, the percentage pullback. Same
   stop, same target, same sizing, same session window.

   This was a small change because of how the engine is written: a BOS and a
   CHOCH run through the SAME code path inside the engine - the only difference
   is which event flag is set. The broken pivot and the new opposite level land
   in exactly the same variables either way, so the strategy needed no new
   plumbing at all, only a wider trigger.

   A BOS is a continuation, so with this on you also trade WITH the 1m trend, not
   only on its turns. Expect several times as many signals.

2. THE COUNTER TABLE  -  ON by default, position selectable
       CHOCH signals        how many main CHOCHs the strategy saw
       BOS signals          same for BOS, or "off" when the switch is off
       Setups armed         signals that passed the rules and got an order placed
       Orders FILLED        those orders that actually traded
       Armed, never filled  placed, then replaced or cancelled before price
                            reached them
       Exit - target        reached the R-multiple target
       Exit - stop          hit the stop
       Exit - opposite sig  cut short by the opposite signal (close and reverse)
       Exit - time flat     closed by the force-flat hour

   The numbers add up exactly:  ARMED = FILLED + NEVER FILLED + the one setup
   that may still be live right now. That identity was checked over 600,000
   simulated bars and it balanced to the unit, so if the table ever looks wrong,
   it is telling you something real rather than miscounting.

   WHAT TO LOOK FOR. If "armed" is large and "filled" is small, the pullback
   percentage is too deep - price is not reaching your limit before the next
   signal replaces it. If "target" and "stop" are both small while "opposite
   sig" is large, your trades are being cut short by the next signal instead of
   being allowed to finish, and the R-multiple target is not really being tested.

  1. Turn OFF "Opposite CHOCH: close and reverse". This is the bigger one. It

================================================================================
THE TWO RULES
================================================================================
Both fire on a MAIN-tier CHOCH on the 1m chart, confirmed on bar close.

RULE 2 - checked first, takes priority
    Condition: the 15m MAIN trend AGREES with the 1m CHOCH direction.
    Entry:     a limit on the pivot the CHOCH candle just broke.
    For a bullish CHOCH that pivot sits below price, so the buy limit is valid.

RULE 1 - the default
    Condition: the 15m trend does NOT agree. Counter-trend, deliberately.
    Entry:     a limit at a percentage pullback, default 50%.
    The leg is measured the way your 50% line measures it - from the live CHOCH*
    level up to the running extreme - using the engine's own f_retLvl(). It
    RATCHETS: each new high moves the level up and the resting order is
    re-placed, a down candle leaves it alone.

STOP        the live CHOCH* level, plus an optional buffer. florS.price - buffer
            for a long, ceilS.price + buffer for a short.
            While the order is still RESTING the stop follows that level as the
            engine moves it. It LOCKS at the moment of fill and does not move
            again.
TARGET      an R multiple of the entry-to-stop distance. Default 1.0.
SIZE        three modes, default risk-based off the stop so every trade loses
            the same cash if stopped - which is what makes the R target mean the
            same thing on every trade. Fixed quantity and fixed cash also there.

SESSION, all three as inputs, timezone Asia/Kolkata by default
    entries taken       06:00 to 23:00
    force flat          02:00, at market, target hit or not
An open trade is NOT closed at 23:00 - only new entries stop and resting orders
are cancelled.

================================================================================
THE ONE THING THAT COULD NOT BE BUILT AS ASKED
================================================================================
You asked that when a trade is running and the opposite CHOCH fires, the new
trade be taken AS WELL. A Pine strategy holds ONE net position. There is no way
to run a long and a short side by side, each with its own stop and target - if
you are long and then enter short, TradingView closes the long. That is the
engine, not a setting.

So the switch "Opposite CHOCH while in a trade: close and reverse" does the
closest thing: closes the running trade at market and opens the new one. Turn it
off and the new CHOCH is ignored until the current trade finishes.

In practice this rarely fires at all. The stop IS the CHOCH* level, and an
opposite CHOCH is by definition a close beyond that level - so the trade is
normally stopped out before the opposite CHOCH can print. It only survives when
the stop buffer is wide enough to sit outside the break.

================================================================================
TWO BUGS FOUND AND FIXED BEFORE RELEASE
================================================================================
The state machine was replayed outside Pine over 720,000 simulated bars with
4,978 fills, checking five invariants on every bar. The first pass found two
real faults, both mine:

1. A STALE SETUP COULD FIRE AFTER A TRADE CLOSED.
   A CHOCH in the SAME direction as a running trade still armed a new setup. No
   order could be placed while the position was open, so it sat there - and the
   instant the trade closed on its stop or target, that stale setup placed an
   order at a level that was by then minutes old.
   FIX: a setup is only accepted when flat, or when it is the opposite CHOCH the
   reverse switch is deliberately acting on.

2. THE STOP COULD END UP ON THE WRONG SIDE OF A RESTING ENTRY.
   Because the pending stop follows the live CHOCH* level, that level can be
   re-anchored upward past a resting rule-2 limit. The sanity check caught it and
   declined to re-place the order - but the order already resting stayed live, so
   it could fill with the stop ABOVE the entry.
   FIX: when the check fails, the resting order is cancelled and the setup
   dropped. It waits for the next CHOCH.

Second pass over the same 720,000 bars: ZERO violations of any of the five
invariants - never both sides resting, never a pending setup surviving a fill,
never in a position without a locked stop, and the bracket always on the correct
side of the fill price for both directions.

================================================================================
BACKTEST REALISM - PLEASE READ
================================================================================
When one 1m bar's range covers BOTH your stop and your target, TradingView
cannot know which came first and assumes the worst case - the stop. On a 1m
chart with 1:1 targets that will happen often, so the reported win rate is
PESSIMISTIC, not optimistic.

Turn on Bar Magnifier in the strategy's Properties tab (paid plans) and it
resolves the order from lower-timeframe data. Also set realistic Commission and
Slippage there before believing any equity curve - both default to zero and zero
is never true.

The 15m trend is read from CONFIRMED 15m bars only, so it updates once every 15
minutes on a 1m chart. That is correct and non-repainting, not lag.

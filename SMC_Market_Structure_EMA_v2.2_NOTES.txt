//         rule, and by then price is often already back through the midpoint.

//  v1.10  THE MTF TABLE STOPS AT THE HIGHEST TIMEFRAME THE CHART CAN
//  ACTUALLY FEED IT.  (v1.8 is withdrawn; this is built on v1.7.)
//    THE PROBLEM, measured rather than assumed. A probe requesting
//    bar_index + 1 from each timeframe reported how many bars request.security
//    really returns. On EURUSD, from a 1m chart, the weekly series came back
//    with NINE bars and the monthly with ONE. The per-timeframe engine is a
//    state machine that replays every pivot and break from the first bar it can
//    see, so one monthly candle does not make it fail — it makes it answer
//    confidently and wrongly. That is where the monthly row reading BULLISH on
//    a 15m chart and BEARISH on a 1h chart came from.
//    THE RULE, which fixes it by not asking the question. A row is drawn only
//    when its timeframe is at or above the chart AND at or below the ceiling
//    the chart can support:
//        chart 5m and below ....... ceiling 4h   (nothing daily or higher)
//        chart 15m ................ ceiling 1W   (daily and weekly, no monthly)
//        chart 10m, 30m, 45m, 1h .. ceiling 1D   (daily is the top row)
//        chart 2h and above ....... ceiling 1M   (everything, through monthly)
//    A 2m chart falls in with 5m and below, and the 61-to-119-minute band with
//    1h and below; neither is named by the rule and both take the conservative
//    side. THE 5m-AND-BELOW CEILING IS WHY: from a 1m chart the daily series
//    comes back with about SIXTY-NINE bars, and on the reported EURUSD chart
//    that row read BULLISH while the daily chart itself read BEARISH. Sixty-
//    nine bars is not a daily structure, so the row is no longer offered.
//    IT IS ALSO THE SECURITY-CALL OPTIMISATION. A row outside the ceiling has
//    its _uX flag false, and a false flag already collapsed that request to
//    timeframe.period — the chart\'s own data, already loaded, costing nothing.
//    So on a 1m chart the weekly and monthly datasets are no longer fetched at
//    all. Fewer real datasets per script is exactly what keeps an alert inside
//    the server\'s budget, which is where the calculation errors came from.
//    The requests stay DYNAMIC, as asked. The same mechanism means an alert
//    created with the table switched off fetches no extra timeframe at all,
//    because tblOn is part of every flag.

//    named constant that both tests read. The flags stay plain inline

//    the thing being avoided here.

//  v1.7  ONE CANDLE CAN NO LONGER SUPPLY A LEVEL AND TRIGGER ITS OWN
//  PROMOTION ON THE SAME BAR.
//    Reported on two charts. FIRST: a single wide candle swept the ceiling AND
//    the floor, and both pivot-2 promotions fired on that one bar, so the whole
//    range collapsed onto that candle — its high became the possible BOS and its
//    low the possible CHOCH, neither of them a pivot anything had confirmed.
//    SECOND: a BOS line anchored back at its original pivot but drawn at the low
//    of a much later candle, because that candle wicked below the floor, closed
//    back above it, and its own high cleared the opposite reference — sweep and
//    trigger on one bar again, so the floor was promoted down to the wick of the
//    very candle that made it.
//    THE CAUSE, and it is the same one both times. The promotion asks two
//    questions: was the level swept, and has price since taken out the opposite
//    reference. Nothing stops BOTH from being answered by the SAME candle. A
//    wide bar wicks through the level and, in the same range, trades past the
//    reference on the other side — so the sweep is recorded and the trigger
//    fires before the bar has even closed, and the level moves to a wick that
//    is one bar old and has been confirmed by nothing.
//    THE FIX, and it is deliberately the narrowest one that works. When the
//    trigger is satisfied ON THE BAR THAT MADE THE SWEPT EXTREME, that sweep is
//    flagged, and while it carries the flag the promotion additionally requires
//    the swept wick to have been confirmed as a pivot by the 3-CANDLE PULLBACK
//    RULE. A wick made on the current bar can never be confirmed on its own bar,
//    so the collapse cannot happen; if the pullback arrives later, the promotion
//    fires then, exactly as before. THE FLAG IS PER SWEEP: recording a new,
//    deeper swept extreme clears it, and a level re-created by any route starts
//    clean.
//    WHAT IS NOT TOUCHED, on purpose. If the trigger arrives on a LATER bar than
//    the sweep — which is the ordinary case, and the GBPCHF sequence v15.14
//    change 2 was written for — nothing is flagged, nothing is checked, and the
//    promotion behaves exactly as it did in v1.6. v15.14 change 2 is intact:
//    an unconfirmed swept wick still takes the level. Only the one-candle case
//    is gated.
//    WHAT THE FIRST CHART NOW DOES: the ceiling is not promoted, so it stays on
//    the original pivot and the break is measured there. The candle then closes
//    through it and the opposite side re-anchors with f_retExtInc, whose window
//    includes the break candle (v15.14 change 1) — so the new floor lands on
//    that candle's low, the deepest point of the leg. The original pivot keeps
//    the BOS, the newest low becomes the CHOCH*, which is the outcome asked for.
//    ALL SIX PROMOTION SITES: main, internal and inner, up-break and down-break.

//  THE 3-CANDLE PULLBACK RULE (Module 1) — swing HIGH; lows mirror
//    1. CANDIDATE = highest high so far; a new OR EQUAL extreme replaces it.
//    2. Three BEARISH pullback candles: c1 = first bearish candle at/after the
//       candidate (its LOW locks); c2 must CLOSE below c1 low; c3 must CLOSE
//       below c2 low -> CONFIRMED.
//    3. Always body-close beyond the previous locked WICK. Never body-to-body.
//    4. Noise PAUSES, never resets. The three need not be consecutive.
//    5. A new OR EQUAL extreme RESTARTS everything.
//    6. Reported on the confirmation bar, ANCHORED at the candidate bar.
//
//  TWO PIVOT STREAMS — never mix them up
//    MAIN      hiT / loT   free-running.  Read by BOS / CHOCH only.
//    INTERNAL  aHiT / aLoT alternating.   Read by iBOS / iCHOCH and nBOS / nCHOCH.
//
//  THREE NESTED ENGINES
//    MAIN     BOS / CHOCH    · anchored on the absolute extreme at chart start
//    INTERNAL iBOS / iCHOCH  · anchored on the main trend-side line pivot
//    INNER    nBOS / nCHOCH  · anchored on the internal trend-side level
//  Each: adopt into an EMPTY slot — an equal-price pivot never takes the level
//  (v15.5) · first break of a range = CHOCH · then with-trend = BOS, against =
//  CHOCH + flip · broken side empties and refills · opposite side re-anchors to
//  the retracement extreme · sweeps arm a pivot-2 promotion.
//
//  INVARIANTS — break these and old bugs come back
//    1. Only a confirmed MAIN event starts a new internal range; only a confirmed
//       INTERNAL event starts a new inner range.
//    2. The range anchor is LATCHED for the life of the range.
//    3. Main = free-running pivots. Internal and inner = alternating.
//    4. A structure level is a CONFIRMED PIVOT, with ONE deliberate exception

v16.0 / v2.0  -  TEN TIMEFRAMES REMOVED FROM THE MULTI-TIMEFRAME TABLE
================================================================================
REMOVED : 2m, 3m, 10m, 30m, 45m, 2h, 3h, 6h, 8h, 12h
REMAINING (8) : 1m, 5m, 15m, 1h, 4h, 1D, 1W, 1M

WHY IT IS WORTH SO MUCH. f_tfPack is the whole structure engine written out
again for one requested timeframe, and Pine INLINES a user function at every
call site. Each timeframe the table requests is therefore another complete
copy of that engine in the compiled script. Removing ten of them removes ten
copies.

    compiled tokens   102,987  ->  about 69,700   (the hard limit is 100,256)
    request.security  18 calls ->  8 calls
    engine instances  18       ->  8, on every bar

The third line is the one that matters beyond the token error: fewer requested
datasets per script is exactly what keeps an alert inside TradingView's
server budget, which is where the "calculation error" alerts were coming from.

WHAT IT COSTS. Deleting an input renumbers every input after it, so the 207
inputs that followed the timeframe checkboxes take their neighbour's saved
value once. That is the table styling, the EMA group, the internal and inner
styling, the alert checkboxes, the arm readout and the 50%-line groups.
Inputs 1 to 330 - every structure colour, the volume profiles and the
killzones - are untouched. Re-set the back half of the panel once and it is
done.

ONE CONSEQUENCE WORTH KNOWING. The row for the chart's own timeframe is the
only one that bypasses request.security and reads the live engine directly.
On a chart set to a timeframe that no longer has a row - 3m, 30m, 2h and the
rest of the removed list - the table simply has no self row. The remaining
rows are unaffected and still correct.

NOTHING ELSE CHANGED. Not one engine rule, not one drawing rule, and no alert.

================================================================================
v16.1 / v2.1  -  ORPHAN TEXT FIXED, AND AN ALERT BUDGET
================================================================================
1. TEXT LEFT ON THE CHART WITH NO LINE UNDER IT.  Reported after switching on
   "keep only the latest 10 marks per tier": ten lines survived, but far more
   than ten words did.

   THE CAUSE was mine. The cap kept N lines and 2N labels, on the reasoning
   that a break can print two pieces of text - the BOS/CHOCH word and the
   strong-point stamp. But a CHOCH never stamps, and with strong marks off
   nothing stamps, so 2N labels covered many more than N breaks. The leftovers
   were the text of breaks whose lines had already been deleted.

   THE FIX is to stop guessing a ratio. Each tier now carries a third array
   recording how many labels each line actually produced: f_addLn pushes a line
   and opens a counter, f_addLb pushes a label and increments the counter of
   the line it belongs to. When f_cutOld drops the oldest line it drops exactly
   that line's labels with it - none, one or two, whichever it made. Applied to
   all three tiers and to the two safety prunes as well, so the pairing holds
   whichever route deletes a mark.

2. "Stop after N alert triggers" in the alert group. 0, the default, is
   unlimited and is exactly how every earlier version behaved. Any other number
   is a budget for the whole indicator: every message counts against it, and
   once spent the indicator goes quiet until the alert is recreated.

   HOW IT WORKS. The twenty-four places that used to call alert() now queue
   their message instead, and one block at the end of the script empties the
   queue, counting as it goes. That keeps the budget in one place rather than
   spread over two dozen call sites, and it is why the setting could be added
   without moving any code.

   ONLY LIVE BARS SPEND IT. Replaying history never consumes the budget, so an
   alert created on a long chart starts with all of it.

   It is one budget for the whole indicator, not one per event: with three
   events ticked and a budget of 3, a single busy candle can spend it all.
   TradingView cannot carry the count across alerts - recreate the alert and
   the budget starts again.

ONE INPUT ADDED, appended at the end. No engine rule changes.

================================================================================
v16.2 / v2.2  -  STRUCTURE-RANGE VOLUME PROFILES, AND MULTI-TIMEFRAME ALERTS
================================================================================
1. THREE STRUCTURE-RANGE VOLUME PROFILES (main file only; the EMA build has no
   volume-profile module to hang them on). Groups 14, 15 and 16. ALL THREE ARE
   OFF BY DEFAULT.

   Each is anchored on the candle that confirmed its tier's last break and grows
   with every candle after it, so it always describes the leg being traded
   rather than a calendar period:
       main     restarts on every confirmed BOS / CHOCH
       internal restarts on every iBOS / iCHOCH, and on any main event
       inner    restarts on every nBOS / nCHOCH, and on any internal or main one

   They reuse the profile engine already in the file - the same VPCol
   accumulator, the same renderer, the same rows and value-area percentage from
   the general profile group - so they cost three accumulators and three
   renders, not a second engine.

   RESOLUTION, stated honestly. They share the intrabar feed the session and day
   profiles use, which is fetched whenever any of those is enabled - MASTER A
   does that by default, so in normal use these get full intrabar resolution.
   Turn every other profile off and there is no intrabar feed to share: they
   fall back to one sample per chart candle. The shape is coarser; the POC and
   value-area levels are still computed correctly from what is there. This was
   a deliberate choice - reading the intrabar feed from a new switch would have
   meant inserting an input halfway up the file and renumbering 249 others.

2. MULTI-TIMEFRAME STRUCTURE ALERTS. Three switches in the alert group: main,
   internal and inner. Each fires when the matching tier of ANY timeframe
   currently listed in the table prints a break, and the message names the
   timeframe. Tick the timeframes you want in the table, tick the tier you care
   about, and one "Any alert() function call" alert covers the lot.

   HOW IT COST ALMOST NOTHING. f_tfPack already returned a fourth value that has
   been permanently zero since the EVENT column was retired for the token limit.
   That slot now carries three bits - main direction, internal, inner - set from
   flags the function already computed. Four short lines inside f_tfPack, and
   they are the only thing in this release that is compiled eight times.

   A HIGHER TIMEFRAME REPORTS AT ITS OWN CLOSE. A 4h break watched from a 15m
   chart arrives when the 4h candle closes, not when price moves through it.
   That is how a higher-timeframe request works, and it is correct.

   Both obey the arming gate and the "Stop after N alert triggers" budget.

35 inputs added to the main file, 3 to the EMA file, all appended at the end.
No engine rule changes.
